# SDLC Day 1 — SDLC는 왜 존재하는가

> 5일 학습 과정 중 1일차 정리. 최종 산출물(사내 게시물)의 1장 초안 역할.

---

## 1. 오늘의 결론 (먼저)

**SDLC가 단계를 나누는 목적은 순서 준수가 아니다.**
각 단계마다 **그 단계에서만 잡히는 결함**이 정해져 있기 때문이다.

그리고 개발 방법론의 역사는 한 문장으로 요약된다.

> **"해석 충돌 시점을 어떻게 앞으로 당길 것인가."**

Waterfall, V모델, Agile, DevOps는 이 하나의 질문에 대한 서로 다른 답이다.
(→ Day 2에서 이 프레임으로 전 모델을 재해석)

---

## 2. 왜 뒤에서 고치면 비싼가

### 현상

결함 수정 비용은 단계가 뒤로 갈수록 폭증한다.
Barry Boehm(1981)이 데이터로 정리했고, 통상 다음 비율로 인용된다.

| 단계 | 상대 비용 |
|---|---|
| 요구사항 | 1 |
| 설계 | 5 |
| 구현·테스트 | 10 |
| 운영 | 100 |

### 메커니즘 (여기가 핵심)

"코드 몇 줄 고치는 비용"이 100배가 되는 게 아니다.
잘못 정의된 요구사항 하나는 테스트 시점까지 오는 동안 **여러 산출물로 복제**된다.

```
잘못된 요구사항 1건
   ├── 설계서
   ├── 화면 설계
   ├── 소스 코드
   ├── DB 스키마
   ├── 연계 인터페이스 규격  ← 타 팀과 이미 합의됨
   └── 테스트 케이스
```

즉 수정 비용의 실체는 두 가지다.

1. **복제본 전부를 되감는 비용**
2. **조직 간 재합의 비용** — 관련 조직이 늘어날수록 여기가 지배적이 된다

> 규제 산업에서 (2)가 특히 크다. 산출물이 승인 절차에 묶여 있으면
> 되감기는 문서 수정이 아니라 **절차 재수행**을 의미한다.

## 3. 왜 하필 테스트 시점에 드러나는가

설계 검토도 했고 문서 리뷰도 통과했는데 결함이 남는다.
**앞 단계 리뷰가 부실했던 것이 아니다.** 리뷰라는 활동이 원리적으로 잡을 수 없는 결함이 있다.

### 핵심 명제

> **문서는 애매함을 허용하고, 코드는 허용하지 않는다.**

예시 — 요구사항 문장:

```
"조회 결과는 최신순으로 정렬한다"
```

이 문장은 리뷰를 통과한다. 세 사람 모두 "이해했다"고 느끼기 때문이다.
그러나 코드로 옮기는 순간 **강제로 하나를 골라야** 한다.

- 등록일 기준인가, 수정일 기준인가
- 동일 시각이면 2차 정렬 키는 무엇인가
- 삭제 건은 포함인가
- 페이징 경계에서 순서가 보장되는가

문서 단계에서는 이 질문들이 **아예 제기되지 않는다.** 애매한 채로도 문장이 성립하기 때문이다.

### 따라서

결함이 드러나는 시점 = **서로 다른 해석이 물리적으로 맞물리는 지점**

- 통합 테스트
- 타 시스템 연계 시험
- 사용자 시연 / UAT

세 사람이 명세서를 읽으면 세 가지로 해석하지만, **읽는 동안에는 그 차이가 보이지 않는다.**
각자 자기 해석이 유일한 해석이라고 믿기 때문이다.

## 4. 두 가지 대응 전략

충돌 시점을 당기는 방법은 원리적으로 둘뿐이다.

### (A) 실행 가능한 것을 더 빨리 만든다

| 수단 | 내용 |
|---|---|
| 프로토타입 / PoC | 화면·흐름을 실물로 확인 |
| 임베디드 DB (H2 등) | 운영 DB 없이 스키마·쿼리 검증 |
| Stub / Mock | 미구현 모듈, 타 팀 API 대체 |
| Mock 서버 (WireMock 류) | 안 열린 연계 시스템 대체 + **장애 응답 주입** |
| Contract Test | 양측을 동일 규격에 결속 |
| 컨테이너 기반 미들웨어 | 실물에 가까운 로컬 검증 |

### (B) 실행하지 않고 충돌을 노출시킨다

| 수단 | 무엇을 강제하는가 |
|---|---|
| 화면 설계서 / 와이어프레임 | "정렬"이 화면에서 어떻게 보이는지 확정 |
| 인터페이스 규격서 (필드 타입·길이·필수여부) | 애매한 문장을 필드 정의로 환원 |
| 데이터 모델 / ERD | 관계와 카디널리티 확정 (1:N인가 N:M인가) |
| **테스트 케이스 선작성** | 기대값을 적으려면 해석을 하나로 골라야 함 |
| 인수 조건 (Given/When/Then) | 애매함이 문법적으로 성립하지 않음 |
| 예외·경계 시나리오 목록화 | 정상 흐름만 볼 때 안 보이던 충돌 노출 |

> (B) 중 가장 강력한 것은 **테스트 케이스를 설계 단계로 앞당기는 것.**
> 기대값을 적는 행위 자체가 해석을 하나로 확정시킨다.
> V모델이 좌측 각 단계에 우측 테스트 레벨을 대응시키는 이유가 이것이다.

## 5. 각 전략의 진짜 병목

| | 전략 | 병목 | 성격 |
|---|---|---|---|
| (A) | 실행을 앞당김 | **거버넌스** — 승인 리드타임, 망분리, 연계 시스템 오픈 시간, 정기 릴리즈 창구, 조직 간 일정 조율 | 비기술 |
| (B) | 실행 없이 충돌 노출 | **경험 축적** — 실패 모드를 떠올리는 능력 | 비기술 |

### (A)의 병목은 엔지니어링이 아니다

컨테이너를 못 띄우는 게 아니고, CI를 못 만드는 게 아니다.
환경 하나를 얻는 데 **신청·승인·일정 조율**이 필요한 것이 병목이다.

### (B)의 병목은 상태공간 열거 능력이다

시나리오를 **쓰는 손**이 아니라 **어떤 조건 조합에서 깨질지 떠올리는 머리**가 병목이다.

요구사항은 "무엇을 해야 하는가"만 적는다. 그러나 결함은 거기서 나오지 않는다.

```
결함이 사는 곳 = 명세에 존재하지 않는 축

  · 무엇이 없을 때        (null, 미등록, 권한 없음)
  · 무엇이 늦을 때        (타임아웃, 지연 응답)
  · 무엇이 절반만 됐을 때 (부분 실패, 트랜잭션 경계)
  · 동시에 일어날 때      (경쟁 조건, 락)
  · 상태가 어긋날 때      (캐시 불일치, 세션 만료, 마이그레이션 중간 상태)
```

이 조건들의 조합은 지수적으로 증가하는데, **명세 어디에도 적혀 있지 않다.**

### 결정적 비대칭

| | 상태공간을 누가 열거하는가 |
|---|---|
| (A) | **세계가 대신 해준다.** 실행시키면 상상하지 못한 조건이 저절로 터진다 |
| (B) | **내 머리로 전부 해야 한다.** 품질 상한이 "겪어본 장애의 총량"에 묶인다 |

→ (B)는 인력을 두 배 투입해도, 산출물 양식을 강화해도 품질이 오르지 않는다.

## 6. 실무 레버

### (A): 실행 가능성과 환경 완전성을 분리한다

> 연계 시스템이 안 열려도, 운영 DB에 접근 못 해도 **실행은 된다.**
> 없는 것을 대체물로 채우면 된다.

특히 Mock 서버는 (B)의 병목까지 건드린다 —
타임아웃·중복 응답·부분 실패를 **의도적으로 주입**할 수 있으므로,
머리로만 상상했던 실패 시나리오를 실제로 실행해볼 수 있다.

#### ⚠️ 함정 1 — 재현도 격차

H2에서 통과한 쿼리가 Oracle에서 깨진다.
방언, 힌트, 시퀀스, 락 동작, 날짜 타입, 문자 인코딩이 모두 다르다.

> "테스트에선 됐는데 운영에서 안 되는" 결함.
> 충돌 시점을 당기려다 오히려 **운영 시점까지 미룬** 결과.

#### ⚠️ 함정 2 — Mock을 누가 만드는가 (더 근본적)

```
내가 이해한 대로 Mock을 만든다
   → Mock이 내 오해를 충실히 재현한다
   → 테스트 전부 초록불
   → 해석 차이가 완벽하게 은폐된다
   → 실물과 붙는 순간 폭발
```

> **잘못 만든 Mock은 (A)를 (B)의 실패로 되돌린다.**

**조건:** Mock은 내 해석이 아니라 **양측이 합의한 규격에서 파생**되어야 한다.
규격 문서에서 Mock을 생성하거나, Contract Test로 양측을 같은 규격에 결속시킨다.
그러지 않으면 Mock은 검증 장치가 아니라 **자기확신 장치**가 된다.

### (B): 개인의 상상력에서 조직의 자산으로

- 장애 이력을 **재사용 가능한 실패 모드 카탈로그**로 전환
- 포스트모템을 감상문으로 끝내지 않고 **체크리스트 항목으로 환원**
- 조합을 기계적으로 열거하는 일은 사람이 약하고 기계가 강한 영역
  → AI 에이전트 활용의 가장 정당한 명분 (Day 5에서 다룸)

## 7. 한 장 요약

```
문서는 애매함을 허용한다  →  코드는 허용하지 않는다
                              ↓
              해석 충돌은 "실행되는 시점"에 처음 드러난다
                              ↓
          단계를 나누는 이유 = 충돌 시점을 앞으로 당기기 위해
                    ↙                        ↘
        (A) 실행을 앞당김            (B) 실행 없이 충돌 노출
        병목: 거버넌스                병목: 경험 축적
        레버: 환경 완전성 분리        레버: 실패 모드 카탈로그화
        위험: Mock이 오해를 은폐      위험: 형식적 산출물로 전락

            둘 다 기술 문제가 아니다 → 도구 도입으로 해결되지 않는다
```

## 8. Day 2 예습 과제

프로세스 모델 비교. 단, **정의 비교는 하지 않는다.**
Day 1의 프레임으로 Waterfall / V모델 / 반복·점증 / Spiral / Agile / DevOps를 재해석한다.

**핵심 질문:** 금융권에 Waterfall이 남아있는 것은 후진성인가, 규제 환경에서의 합리적 선택인가.

**생각해올 것 (5분)**

1. 진행 중인 차세대 프레임워크 전환 과제는 어떤 모델로 돌아가는가?
   공식 명칭이 아니라 **실제로 작동하는 방식**으로.
2. 그 방식은 (A)와 (B) 중 어느 쪽에 의존하고 있는가?
